# Barcode-Scan und Produktsuche Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** In the meal tracker the user scans a barcode or searches a product by name; core fetches it from Open Food Facts, recognises its ingredients like a photo's, and the tracker is filled with the product name and those ingredients.

**Architecture:** Core gets one route `product-lookup` (`barcode` or `q`) that alone talks to OFF (`app/off.py`), caches products in an api-only table `products`, turns OFF's ingredients text into app ingredient names with one cached AI pass per product (deterministic fallback), and matches them per user with the catalogue code moved out of `analyze-meal`. The app gets a product sheet (scanner behind a provider, search, result card) that returns a `ProductPrefill`, which `MealTrackerNotifier.applyProduct` merges into the meal; the tracker stays the edit step.

**Tech Stack:** core: FastAPI, SQLAlchemy async, alembic, httpx2, `app.ai.call_claude`, pytest + respx. App: Flutter, Riverpod, GoRouter, supabase_flutter, plus `mobile_scanner` (new unless the portal track added it first).

**Spec:** `docs/superpowers/specs/2026-11-27-barcode-design.md` (app repo, branch `docs/plan-barcode`). Section numbers (§) below refer to it.

- `products` has no user column; nothing records which user scanned what.
- No OFF image is fetched, shown or stored, in core or app.

- Scanning and search are free (not behind the paywall switch).
- `mypy --strict`; synthetic test data only; route-test fixtures delete the `profiles` row as well as the `auth.users` row (use the existing `NewUser`/`Db` fixtures).
- No privacy-policy version bump in this plan: the §5 paragraph goes into the controller's shared „policy text" task.
- Values marked „verify at build time" in the spec (OFF endpoints, fields, limits, the add-product URL): check them against OFF's current docs before BC1 and note the result in the PR; change only `app/off.py` and the fixtures if they differ.
- Conventional commits; PRs to `develop`; never merge, never auto-merge; stop at `gh pr create`. Nothing here changes a production host, DNS, secrets or a third-party account.

## Review Focus

1. **A barcode that is not a valid product code** (bad check digit, 12-digit UPC-A, letters, a QR payload from the portal's scanner): core answers 400 `invalid_barcode` or normalises UPC-A to `0`+13 digits; the app scanner only reports EAN-13/EAN-8/UPC-A. Tests in BC1 (`normalise_gtin`) and BC5.
2. **OFF answers oddly or not at all** (HTTP 404 with `status: 0`, a product without German fields, without a name, without ingredients, a timeout, a 503 — with and without a stale cache row): not found / English text / empty list / stale row answers / 502 `off_unavailable`. Tests in BC1 and BC5.
3. **A messy ingredients text** (percentages, „Süßungsmittel: Sorbit", E-numbers, nested brackets, English) and **the AI failing on it**: polyols kept, other additives dropped, fallback names matched but not inserted and not cached, retried next time. Tests in BC3 and BC5.
4. **Many requests** (one user hammering search; all users together past OFF's per-IP limit): per-user 429 `throttled`, global 429 `off_busy` unless a cached row answers; search terms never logged. Tests in BC5.
5. **Applying a product to a tracker that already has content** (own title, photo, overlapping ingredient „hafer" vs „Hafer"; camera denied; offline): title kept, ingredients merged case-insensitively, photo untouched; denied camera still leaves search usable; offline shows the fallback text with „Nochmal versuchen". Tests in BA3 and BA4.
